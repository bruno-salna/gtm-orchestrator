# Step 2: Write the Run Brief

## Goal
Ask every question the guides in this run will need, once, and write the answers into one brief, before any data is shown.

## Why it matters
Each guide opens by asking what the user sells, who their customers are and how many accounts the team can work. Run four guides one after another and the user answers the same questions four times, with slightly different answers each time. One brief gives every guide the same facts.

The order matters too. The ICP + tiering and Signals guides both ask for the user's beliefs before showing any data, so the findings don't steer the answer. In a chain, the Market map would already have shown the market by the time tiering starts. Asking the beliefs here, at the very start, keeps them clean.

## How
1. **Copy [../run-brief-template.md](../run-brief-template.md)** into the run folder as `run-brief.md`.
2. **Leave out what this run doesn't need.** A run that starts at Signals doesn't need the market definition or the list's source. Ask only the sections for the guides that will run.
3. **Ask section 2 (beliefs) before anything else that shows data.** Write the answers in the user's own words. Don't summarise them; the ICP + tiering and Signals guides compare their findings against exactly what was said.
4. **Ask for one customer file** with register IDs, groups and start dates. Both ICP + tiering and Signals use it. If the user has groups but no start dates, ICP + tiering can still use it; Signals will be on path C.
5. **Ask capacity once,** as people × accounts each per month, and work out both numbers: tier 1 size for the tiering period, and `now` capacity for the next month. Show the user both, so they see one number grows from the other.
6. **Fill in the defaults in section 6** and ask the user to confirm or change them.
7. **Set the provisional evidence paths** from the customer count. Each guide confirms its path after matching; the brief only records the starting expectation.
8. **Get the user's sign-off** and note it in the run log.

## How the guides use the brief
When a guide starts, its step 1 still runs, in full. The difference is that you fill in its worksheet from the brief, show it to the user, and ask only what's missing or has changed. The user signs off the guide's step 1 as usual.

| Brief section | Market map | List quality | ICP + tiering | Signals |
|---|---|---|---|---|
| 1. Offer and market | step 1 | step 1 (scope) | step 1 (hard limits) | step 1 |
| 2. Beliefs | | | step 1 (ICP belief) | step 1 (why customers bought) |
| 3. Customers | step 1 (optional) | | step 1 (groups, "best") | step 1 (start dates) |
| 4. Capacity | | step 1 (size check, outreach) | step 1 (tier 1 size) | step 1 (`now` capacity) |
| 5. The list | | step 1 | | |
| 6. Settings | step 1 (map use) | step 1 (preset) | | step 1 (look-back, web checks) |

## Pitfalls
- **Asking for the brief, then showing the market map first.** If the map is shown before section 2 is written, the beliefs are no longer blind. Write them first.
- **Two capacities that don't match.** "40 accounts a month" for tiering and "100 accounts this month" for signals means one answer is wrong. Ask once and derive both.
- **Treating the brief as final.** Answers change as the guides run: a new hard limit at tiering, a different start-date definition at signals. Update the brief, and log the change and the reason.

## Done when
`run-brief.md` holds every section this run needs, the beliefs were written before any data was shown, both capacities come from one answer, and the user has signed it off.
